# План развития рантайма DagFlow


Основное направление: сохранить локальные deque, шардированные центральные очереди и work stealing; переработать модель завершения графа; затем уменьшать стоимость планирования и управления памятью.

## Статус реализации

Основной этап реализован в рабочем дереве. Текущие контракты описаны в
[архитектуре рантайма](how_it_works.md), измерения — в
[отчёте бенчмарков](runtime-benchmark-results.md).

| Направление | Статус |
| --- | --- |
| Завершение при ошибках, отмене и overflow | Реализовано: считаются принятые драйверы исполнения, не все теоретические токены |
| Барьер после многотокенного узла | Реализован: successors открывает последняя lane |
| Жизненный цикл графа | Отдельное состояние запуска, повторные последовательные run, reset/clear после завершения, cancel |
| Scope и parallel_for | Повторные явные запуски; wait/деструктор не запускают завершённый граф повторно; индексы блоков принадлежат запуску |
| Ошибки Pool и алгоритмов | Сохранение ошибки в Handle, explicit rethrow, корректный откат частичной подачи |
| combine | Рёбра завершения без ожидающих задач, итеративное распространение |
| Scheduler bypass | Итеративное исполнение совместимых successors с бюджетом 64 шага |
| Справедливость входа | Опрос центральных очередей каждые 32 получения задачи, ротация шардов |
| spawn/enqueue | SubmissionMode выбирает локальное порождение либо общий вход для worker |
| Память Task | Собственный slab-пул удалён; выбор mimalloc (по умолчанию), tbbmalloc или system через CMake |
| Удерживаемая память | Политика выбранной библиотеки; Pool::memory_stats удалён вместе с собственным аллокатором |
| Память графа | Рёбра и per-run счётчики в непрерывных массивах; определения узлов пока выделяются отдельно |
| Владение | shared_ptr удалён из runtime; unique-владение графом/состоянием/данными операции, передача custody пакета и move-only CompletionCredit |
| Handles | Наблюдатели с intrusive-ссылками на результат; references отделены от credits; payload освобождается перед ready |
| Тесты | Регрессии корректности, отказы выделения, справедливость, память, ASan/UBSan и TSan |
| Измерения | Сохранено прежнее сравнение; оно предшествует замене владения и аллокатора и не описывает текущую производительность |
| Установка package | Требуется smoke test для shared/static consumer и allocator dependency |

По результатам этого этапа **не внедрены** альтернативные MPSC inbox, участие
caller в качестве нового исполнителя и замена линейного поиска спящих workers.
Они остаются отдельными экспериментами: необходимости
замены очередей измерения не установили, а остальные варианты требуют
самостоятельной оценки и протоколов времени жизни. Bypass сокращает операции
планировщика, но не устраняет универсальные ScheduledTask-обёртки на границах
публикации. Измерения также показывают регрессии отдельных нагрузок, а не
универсальное ускорение.

Дальнейшие разделы 1–7 описывают исходный обзор и порядок работ. Упоминания
«сейчас» в исходных наблюдениях относятся к снимку до реализации. Предложения
из исходного обзора о собственном аллокаторе и сохранении shared_ptr заменены
решением из [документа о явном владении](explicit-ownership.md).

## 2. Подтверждённые проблемы корректности

### 2.1. Отмена и переполнение нарушают завершение

Источник: [src/task_graph.cpp](../src/task_graph.cpp), `enqueue_tokens`, `execute_node`.

Воспроизведены следующие случаи:

| Условия | Результат |
| --- | --- |
| `tokens=2`, `capacity=1`, `Overflow::Block` | `run()` не возвращается |
| `tokens=2`, `capacity=1`, `Overflow::Drop` | `run()` возвращается, `wait()` не завершается |
| `tokens=2`, `capacity=1`, `Overflow::Fail` | `run()` возвращается, `wait()` не завершается |
| Два токена, стандартная concurrency, исключение на первом выполнении | `wait()` не завершается |

При `Block` сначала добавляются все токены и только затем запускается обработка. Если capacity меньше их числа, освобождать место ещё некому. При отбрасывании и отмене часть токенов остаётся учтённой в completion, хотя больше не будет выполнена.

Направление исправления:

- Каждый учтённый токен должен ровно один раз перейти в терминальное состояние: выполнен, отменён или отброшен.
- При ограниченной capacity обработка должна начинаться до ожидания свободного места.
- Worker не должен занимать единственный доступный поток, ожидая работу, которую ещё предстоит выполнить этому же пулу.
- Ошибка публикации задачи также должна корректно закрывать или откатывать учёт работы.

### 2.2. Зависимость открывается раньше завершения узла

Источник: [src/task_graph.cpp](../src/task_graph.cpp), `execute_node`.

Каждое выполнение токена уменьшает `remaining_predecessors` successors, хотя этот счётчик описывает число узлов-предшественников. В примере с двумя токенами зависимый узел увидел одно завершённое выполнение при итоговом количестве два. Для воспроизводимого порядка использовались один worker и высокий приоритет successor.

Это нарушает ожидаемый барьер после многократного исполнения узла, в том числе после `parallel_for`.

Предложение: отдельно учитывать оставшиеся исполнения узла. Его successors уведомляет только последнее завершение, ровно один раз на ребро. Политику распространения отмены следует определить отдельно от успешного завершения.

### 2.3. Исключения в алгоритмах оставляют незавершённый handle

Источник: [include/dagflow/thread_pool.hpp](../include/dagflow/thread_pool.hpp), `for_each`, `for_each_ws`; [src/thread_pool.cpp](../src/thread_pool.cpp), `execute_task`.

В алгоритмах `complete()` вызывается после пользовательской функции. Исключение пропускает этот вызов, затем поглощается исполнителем пула. Зависание `for_each` подтверждено на одном элементе; аналогичный путь в `for_each_ws` выявлен по коду.

Предложение: гарантировать завершение через RAII, сохранять первую ошибку в состоянии операции и определить единый способ её получения. Для detached-задач нужен явный контракт обработки ошибок.

### 2.4. Изменение sealed-графа обходит проверку циклов

Источник: [src/task_graph.cpp](../src/task_graph.cpp), `add_edge`, `seal`.

После успешного `seal()` добавление ребра не инвалидирует состояние `Sealed`. В проверке добавление обратного ребра создавало цикл, но повторный `seal()` возвращал `true`.

Предложение: инвалидировать валидацию при изменении структуры либо запретить структурные изменения sealed-графа явным контрактом.

### 2.5. Деструктор графа может блокировать worker

Источник: [src/task_graph.cpp](../src/task_graph.cpp), `TaskGraph::~TaskGraph`.

Деструктор использует блокирующий `Counter::wait()`. Создание и запуск локального графа внутри задачи однопоточного пула приводят к deadlock при выходе из области видимости: дочерняя работа остаётся в очереди этого пула.

Предложение: использовать кооперативное ожидание через `Pool::wait()`, сохранив корректное время жизни состояния запуска до последнего обращения исполнителя.

## 3. Модель графа и запуска

### 3.1. Разделить описание графа и состояние исполнения

Сейчас узлы содержат одновременно функции, рёбра и изменяемые счётчики. Граф навсегда остаётся в `Running` после старта. По коду `clear/reset` после выполнения недоступны, а повторный `run()` сообщает о цикле вместо причины, связанной с жизненным циклом.

Предлагаемое разделение:

| Объект | Содержимое |
| --- | --- |
| Описание графа | Функции, рёбра, настройки узлов, результат валидации |
| Состояние запуска | Оставшиеся зависимости и исполнения, активные задачи, отмена, ошибка, завершение |
| Handle | Владение доступным пользователю состоянием результата |

Жизненный цикл должен явно различать построение, готовность, активное выполнение и терминальные состояния. Завершение вычисления и освобождение его памяти — разные события.

Разделение создаёт основу для повторных запусков. В текущем коде индексы
`GraphScope::parallel_for` принадлежат конкретному запуску, а одновременные
запуски одного описания запрещены явным контрактом.

### 3.2. Зафиксировать значение token и capacity

Для текущего DAG предлагается исходный контракт: узел выполняется N раз, затем открывает successors.

Нужно явно определить:

- Ограничивает ли capacity только ожидающие исполнения или все незавершённые, включая активные.
- Как `Drop` влияет на завершение узла и его successors.
- Останавливает ли `Fail` весь запуск.
- Как обрабатывается нулевая capacity.
- Какие границы числа токенов поддерживаются: сейчас `size_t` преобразуется в `int` при расчёте completion.

Потоковый pipeline с постоянным поступлением токенов потребует самостоятельного контракта допуска, зависимостей и завершения.

## 4. Очереди и планировщик

### 4.1. Сохранить шардированный вход внешних задач

Текущая схема:

```text
Внешний submit → центральный MPMC-шард → worker
Внутренняя работа → локальная deque → текущий worker или thief
```

Единственная глобальная очередь не обязательна. Однако нужен безопасный путь передачи внешних задач: внешний поток не может писать в owner-only Chase–Lev deque.

| Вариант | Преимущество | Цена |
| --- | --- | --- |
| Одна общая MPMC | Простой поиск и подача | Конкуренция за общие индексы |
| Шардированные MPMC | Распределение конкуренции, несколько consumers | Поиск работы между шардами |
| MPSC inbox на worker | Один consumer, адресная доставка | Занятый worker задерживает inbox; нужен механизм перераспределения |
| Участие вызывающего потока | Возможность начать работу без передачи другому потоку | Слоты исполнителей, TLS, ограничения concurrency и вложенность |

Рекомендация: оставить существующие MPMC до измерений, подтверждающих преимущество замены.

В oneTBB есть общий для arena `my_fifo_task_stream` для enqueued-задач. В просмотренной реализации поток разбит на lanes с очередями и mutex. Это пример сочетания локального исполнения и общего входа, а не требование копировать конкретный контейнер. Источники: [arena.h](https://github.com/uxlfoundation/oneTBB/blob/master/src/tbb/arena.h), [task_stream.h](https://github.com/uxlfoundation/oneTBB/blob/master/src/tbb/task_stream.h).

### 4.2. Добавить scheduler bypass

В цепочке коротких узлов постановка единственного готового successor в deque и немедленное извлечение создают лишнюю работу.

Предложение:

```text
A завершён → выбран готовый B → worker продолжает выполнение с B
                         └──→ остальные готовые узлы публикуются для stealing
```

Внутренний исполнитель может возвращать дескриптор следующего готового узла. Продолжение выполняется циклом, без роста стека. Переход допустим только после обычных проверок допуска, зависимостей и concurrency.

Нужен бюджет последовательных продолжений, после которого проверяется другая работа и приоритеты. Учёт завершения и времени жизни обязан включать задачи, исполняемые через bypass.

Это первый кандидат на ускорение цепочек. Источник идеи: [oneTBB Task Scheduler Bypass](https://uxlfoundation.github.io/oneTBB/main/tbb_userguide/Task_Scheduler_Bypass.html). Ускорение для DagFlow пока не измерено.

### 4.3. Разделить локальное порождение и независимую подачу

Предлагаемые внутренние операции:

- `spawn`: продолжение текущего вычисления, локальная deque или bypass.
- `enqueue`: независимая работа, общий вход с регулярным обслуживанием.

Текущий API уже различает эти режимы через `SubmissionMode::Spawn` и
`SubmissionMode::Enqueue`. Worker может явно отправить независимую работу во
входной MPMC-путь; внешний producer по-прежнему использует общий вход.
Дальнейшая задача — измерить, достаточно ли этой политики, а не добавлять ещё
одну очередь заранее.

В TBB локальный выбор задач ориентирован на локальность, а enqueued-задачи имеют отдельный механизм продвижения. Источники: [How Task Scheduler Works](https://uxlfoundation.github.io/oneTBB/main/tbb_userguide/How_Task_Scheduler_Works.html), [arena.h](https://github.com/uxlfoundation/oneTBB/blob/master/src/tbb/arena.h).

### 4.4. Проверить справедливость и стоимость пробуждений

Наблюдения по коду:

- Локальные очереди обслуживаются раньше центральных; непрерывное локальное пополнение может задерживать внешнюю работу.
- Высокий приоритет не является глобальным строгим порядком: локальная normal-задача может выбираться раньше high-задачи в другом источнике.
- `notify_one_idle()` линейно просматривает workers на пути подачи задач.
- Переполнение локальной и центральной очередей вызывает inline-исполнение, которое при рекурсивной подаче может увеличивать глубину стека.

Кандидаты: периодическая проверка внешнего входа, бюджет обслуживания приоритетов, учёт спящих workers, пакетные уведомления. Изменения парковки должны сохранять защиту от потерянных пробуждений.

### 4.5. Участие вызывающего потока

Рассмотреть отдельный режим `run_and_wait()`, в котором caller получает слот исполнителя и помогает выполнять граф. Особенно интересны короткие вычисления, где передача спящим workers заметна по стоимости.

Потребуются ограничения общего числа исполнителей, корректная регистрация локальных очередей и обработка вложенных вызовов. Одного назначения TLS недостаточно.

Источник идеи: [oneTBB task_arena::execute](https://uxlfoundation.github.io/oneTBB/main/specification/source/task_scheduler/task_arena/task_arena_cls.html).

### 4.6. Убрать ожидающие задачи из combine — выполнено

`Pool::combine()` регистрирует completion edges в состояниях входных handles и
не создаёт ожидающие scheduler tasks. Регистрация уже завершённого входа,
гонка с terminal transition, распространение первой ошибки и глубокие цепочки
проверены отдельными тестами. Дальнейшие изменения допустимы только при
сохранении этого свойства.

## 5. Владение, завершение и память

### 5.1. Явные роли объектов

В рантайме разделены четыре разные вещи, которые нельзя заменять одним
счётчиком или одним умным указателем:

| Роль | Текущий механизм | Правило |
| --- | --- | --- |
| Storage ownership | `OwnedObject<T>` и `ObjectDeleter<T>` | Ровно один явный владелец объекта; `release()` означает передачу custody |
| Packet custody | локальный owner → scheduler queue → executor | В каждый момент только один участник может уничтожить `ScheduledTask` |
| Liveness | move-only `CompletionCredit` | Кредит можно только перенести, fork требует живого кредита, retirement ровно один раз |
| Observation | копируемый `Handle` | Handle ждёт и читает ошибку, но не получает право порождать работу |
| Borrowed access | raw pointer под живым credit | После terminal completion обращение к graph/run definition запрещено |

`shared_ptr` в runtime не используется. Это не означает исчезновение учёта
времени жизни: storage, custody, credits и borrowed access проверяются разными
инвариантами. Полная схема зафиксирована в
[документе явного владения](explicit-ownership.md).

### 5.2. Инварианты RunState и completion

Для каждого запуска нужен один монотонный `outstanding work` или эквивалентный
ему набор completion credits. Принятие единицы работы увеличивает учёт ровно
один раз; любой terminal outcome — success, cancel, drop или failure-to-publish
— уменьшает его ровно один раз. Terminal состояние наступает только после
обнуления учёта. Отдельно проверяется, что после terminal zero нельзя получить
новый credit, а каждый spawner сам защищён уже существующим credit.

В текущем коде это выражено sentinel/lane credits: completion не равен числу
теоретических токенов и не равен `Pool::outstanding_`. Если потребуется отдельный
счётчик в `RunState`, он должен оставаться bookkeeping-слоем поверх того же
протокола и не дублировать право на завершение. Для любого варианта сохраняются
правила:

- payload уничтожается до публикации `Handle::ready()`;
- ошибка записывается до terminal notification;
- successor открывается только после барьера последней lane;
- cancellation закрывает все ещё не запущенные единицы работы;
- `combine()` добавляет completion edge без scheduler task;
- глубокие цепочки propagated итеративно, без роста стека.

### 5.3. Выбор библиотечного аллокатора

Собственный slab/free-list/remote-return allocator не является частью текущего
плана. `runtime_memory.hpp` оставляет тонкий адаптер с aligned allocation и
constructor-failure rollback:

| CMake option | Backend | Назначение |
| --- | --- | --- |
| `DAGFLOW_ALLOCATOR=mimalloc` | mimalloc, default | Обычная production-сборка |
| `DAGFLOW_ALLOCATOR=tbbmalloc` | oneTBB scalable allocator | Сравнение с экосистемой TBB и альтернативный production backend |
| `DAGFLOW_ALLOCATOR=system` | `operator new/delete` | Санитайзеры, отказоустойчивость и отсутствие внешней зависимости |

Backend применяется к runtime objects: task packets, completion states, graph
nodes/run-state и operation payloads. STL buffers, per-run arrays and user data
retain their normal allocation paths. DagFlow не переопределяет глобальные
`new/delete` и не обещает allocator-specific RSS или reuse guarantees.

Проверять нужно не только скорость выделения, но и cross-thread destruction,
over-aligned types, constructor exceptions, freeing after producer thread exit
и удерживаемую память после всплеска. Если профилирование покажет, что внешняя
библиотека недостаточна, собственный allocator станет отдельным экспериментом
с независимым протоколом stable storage, remote free и reclamation; его нельзя
встраивать в scheduler без измеренного ограничения.

### 5.4. Память графа и packet lifecycle

Описание графа остаётся persistent и владеет definitions/edges. `RunState` владеет
только per-run arrays and terminal result; task closures borrow it under a live
credit. Перед публикацией packet находится в `OwnedObject<Task>`, после успешной
публикации ownership transferred to the scheduler, а после acquisition — executor.
Executor сначала переносит completion credit, затем уничтожает callable и packet,
и только после этого retires credit и уменьшает pool outstanding. Queue никогда
не владеет storage отдельно от custody.

Следующие оптимизации остаются measurement-driven: compact `{run,node_id}` packet,
меньше lambda wrappers на bypass, batching публикаций и pre-reserved graph arrays.
Ни одна из них не должна ослаблять graph-completion barrier или превращать raw
borrow в скрытое shared ownership.

## 6. План проверки

### Регрессии корректности

- Capacity меньше числа токенов для всех overflow-политик.
- Исключение и отмена при нескольких ожидающих и активных токенах.
- Successor после многотокенного узла и после `parallel_for`.
- Ошибки `for_each` и `for_each_ws`.
- Добавление цикла после `seal()`.
- Уничтожение активного графа внутри однопоточного пула.
- Жизненный цикл clear/reset/run согласно выбранному контракту.
- Ошибки выделения памяти и частичной публикации работы.
- Возврат памяти после stealing, уничтожение из другого потока, завершение
  producer thread, позднее освобождение handle и aligned payload.

Для изменений синхронизации и владения дополнительно использовать санитайзеры. Существующий тест перехвата `new/delete` следует запускать отдельно от TSan согласно [описанию текущей организации кода](code_organization.md).

### Производительность

| Нагрузка | Что позволяет оценить |
| --- | --- |
| Цепочка коротких задач | Bypass и стоимость перехода между узлами |
| Fan-out / fan-in | Публикация параллелизма и стоимость зависимостей |
| Внешний submit с одним и несколькими producers | Конкуренция на входе, выделение и возврат Task |
| Вложенный spawn с активным stealing | Локальные кеши и межпоточные возвраты |
| Неравномерный parallel_for | Балансировка и гранулярность |
| Короткие всплески после простоя | Пробуждения и задержка начала работы |
| Внешние задачи на фоне непрерывного локального spawn | Справедливость обслуживания |
| Большой всплеск с последующим простоем | Пиковая и удерживаемая память |

Фиксировать throughput, общее время, p50/p95/p99 задержки начала задачи, обращения к системному аллокатору, пиковую и удерживаемую память. По возможности добавлять счётчики stealing, уведомлений и системных пробуждений.

Сравнения проводить при одинаковых compiler flags, числе потоков, affinity и workload. Разделять холодный запуск и прогретое состояние. Исторические цифры README не заменяют новую базовую линию.

## 7. Предлагаемый порядок работ

| Этап | Результат |
| --- | --- |
| 1. Корректность | Завершение при ошибках, отмене и overflow; правильные зависимости; регрессионные тесты |
| 2. Контракты и жизненный цикл | Определённая семантика токенов и capacity, разделение graph/run, понятные терминальные состояния |
| 3. Базовые измерения | Воспроизводимые сценарии, учёт аллокаций и задержек |
| 4. Исполнение DAG | Компактное состояние запуска, дескрипторы узлов, scheduler bypass |
| 5. Владение и backend памяти | Явные custody/credit/observation роли, выбранный библиотечный allocator, rollback и cross-thread free |
| 6. Политики scheduler | Справедливость, уведомления, гранулярность; участие caller при подтверждённой пользе |
| 7. Пересмотр очередей | Изменение топологии только при наличии измеренного ограничения |

Этапы оптимизации могут менять порядок после профилирования. Для каждого
изменения нужны сравнение с базовой линией, контроль корректности и отдельная
проверка времени жизни; увеличение числа функций или очередей само по себе не
является целью. До новых замеров benchmark-таблицы из старого отчёта нельзя
использовать как характеристики текущего allocator/backend.

## 8. Следующие действия

1. Зафиксировать интеграционный smoke test для установленного shared и static
   package: `find_package(DagFlow)` должен подтягивать выбранный allocator
   dependency и собирать потребителя.
2. Повторить один и тот же benchmark для `mimalloc`, `tbbmalloc` и `system`;
   сохранить throughput, p50/p95/p99, allocation count и удерживаемую память
   отдельно от исторического отчёта.
3. Прогнать длительные graph/range workloads под ASan/UBSan и TSan после любых
   изменений в credit propagation, packet custody или parking.
4. Проверить invariant-аудитом каждую новую оптимизацию: она не должна
   добавлять второе владение packet, продлевать raw borrow за terminal zero или
   смешивать `Pool::outstanding_` с логическим completion RunState.
5. Только при измеренном ограничении рассматривать caller participation,
   alternate inbox topology или собственный allocator. Для собственного
   allocator заранее потребуются тесты stable storage, remote free,
   reclamation и over-aligned objects.
